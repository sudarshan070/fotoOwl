# Decisions Log

One line per non-obvious choice, appended live during implementation — this feeds the README's "what was cut and why" section directly, so it's written in the moment, not reconstructed at the end.

- **2026-08-08 — Scope cut: web track only.** `media-native` and `media-ui-native` are not implemented in this pass. The spec's app deliverable is React web; building both platforms in the same ~9hr budget would have thinned every layer rather than delivering two solid ones. `media-core`'s API and the `media-ui-react` prop-getter shapes are designed so a native wrapper/component pair could be added later without changing either. Confirmed with the requester before starting implementation.
- **2026-08-08 — useLightbox ships a simplified focus model, not a full cyclic focus trap.** Focus moves into the dialog on open and Escape/Arrow keys work via a document-level listener, but Tab does not yet wrap from the last focusable element back to the first. Full trap cycling was cut for time; the prop-getter shape (`getOverlayProps` returning `ref`/`role`/`aria-modal`/`tabIndex`) doesn't need to change to add it later.
- **2026-08-09 — Dogfooding `skill-wiring-data.md` and `skill-using-components.md`: one real mismatch found and corrected, plus one real gotcha hit and documented.** Writing the two skill docs against the completed `SearchPage`/`LightboxOverlay`/`ReelsView` code (Tasks 1-3) rather than from memory turned up:
  - **Mismatch (fixed in `skill-wiring-data.md`):** the drafted doc claimed "all three" data hooks (`useMediaSearch`, `useCuratedMedia`, `useMediaItem`) return the same `{ items, loading, error, hasMore, loadMore }` shape. That's wrong — only the first two do. `useMediaItem` is not paginated and actually returns `{ item, loading, error }` (see `packages/media-react/src/use-media-item.ts`). Corrected the doc to call out `useMediaItem`'s distinct shape explicitly instead of lumping it in.
  - **Real gotcha hit during Task 3 (documented in `skill-using-components.md`'s `useLightbox` section):** `useLightbox` never reconciles `currentIndex` when the `items` array it was given shrinks. Submitting a new search query while the lightbox was open (commit `8cef896`) left a stale `currentIndex` pointing past the end of the new, shorter results array, crashing on `currentItem.type`. Fixed in `SearchPage.tsx` by closing the lightbox on every new search submission, and added this as an explicit caution in the skill doc so the next consumer resets/closes anything keyed off an index whenever the underlying `items` can change out from under it.
  - Everything else checked — `MediaProvider`/`useMediaClient` ownership of the single client, `useMediaSearch`/`useCuratedMedia` param-serialization-not-identity refetch keying, `useMediaEvents`/`useTrackMediaEvent` subscribe/unsubscribe and default console logging, and every `useGrid`/`useLightbox`/`useReelSwiper` prop-getter name, shape, and documented cut (sentinel-must-be-rendered, disabled boundaries, no Tab-trap, scroll-snap style merging, IntersectionObserver height/overflow requirement) — matched the real implementation in `packages/media-react/src` and `packages/media-ui-react/src` exactly, since both were written from the same frozen `ARCHITECTURE.md` signatures.
- **2026-08-10 — `apps/web` restyled to match fotoowl.ai's actual brand (this app is a take-home submission to FotoOwl), but their proprietary logo asset was not copied in.** Pulled fotoowl.ai's real shipped CSS to extract genuine tokens rather than guessing: primary gold `#fdbf36` (their `--color-primary-500`), dark navy secondary scale (`#283246`→`#10161e`), and `Plus Jakarta Sans` typography, all applied via a new `apps/web/src/theme.css` (styling stays entirely inside the app per the headless-component constraint — `media-ui-react` remains styleless). Deliberately did not download/embed their actual SVG logo file, since redistributing another company's trademarked asset from this repo isn't appropriate even in an assignment context; used a plain 🦉 emoji + text wordmark instead. All prop-getter contracts (`useGrid`/`useLightbox`/`useReelSwiper`) are unchanged — only markup/CSS in `apps/web` was touched.
- **2026-08-10 — Fixed a real reel-autoplay bug: `autoPlay` was being toggled reactively as a React prop, which doesn't work.** `ReelsView` set `autoPlay={index === activeIndex}` on each `<video>`, but the HTML `autoPlay` attribute only takes effect when the element first mounts — flipping the prop after that (which is exactly what happens every time the user scrolls to a new reel) does nothing. Every reel after the first one just sat on its first frame instead of playing. Fixed by tracking each video's DOM node in a ref and calling `.play()`/`.pause()` imperatively in a `useEffect` keyed on `activeIndex`.
- **2026-08-10 — Spec-compliance audit against `senior-react-dev-task-headless-media-sdk.md` before pushing: dependency direction, auth, event pattern, caching, and headless-component requirements all re-verified directly against the code (not from memory) — see the grep/read commands in this session.** All held. One real, concrete instance of the skill docs steering a live code change (not just retrospective dogfooding) surfaced in the same pass: `skill-using-components.md`'s accessibility note — "None of these hooks ships visible focus styles. Add your own `:focus-visible` CSS on interactive elements" — was checked against `apps/web/src/theme.css` and found genuinely unmet: only `.search-input` had any focus treatment; the grid tiles, tabs, search button, and lightbox controls had none. Added a single `button:focus-visible, input:focus-visible` rule (covers every interactive element in the app, since they're all `<button>`/`<input>`) directly in response to that documented requirement, and removed a stray `outline: none` on `.search-input` that would otherwise have suppressed it.
- **2026-08-10 — Known gaps remaining at push time, disclosed rather than silently shipped:** (1) `media-native`/`media-ui-native` are not built (see the scope-cut entry above). (2) The three `vercel.json` configs exist but nothing has actually been deployed yet, and `README.md`'s deploy-URL and AI-chat-transcript-link fields are still TODOs — both require the requester's own Vercel/GitHub accounts and a decision on how to share this chat, so they were left for the requester rather than guessed at.
- **2026-08-11 — `apps/web`'s real Vercel deploy failed on the first attempt: `vercel.json`'s `buildCommand` (`pnpm --filter web build`) never built its workspace dependencies.** This was invisible in every local build because `media-core`/`media-react`/`media-ui-react`'s `dist/` folders already existed from prior local builds — a fresh Vercel checkout has none of that, so Vite failed to resolve `media-react`'s package entry (`Failed to resolve entry for package "media-react"`). Fixed by switching the build command to `pnpm turbo run build --filter=web`, which uses `turbo.json`'s `dependsOn: ["^build"]` to build dependencies first. Verified by fully deleting every `dist/`/`.turbo`/`storybook-static` folder locally (simulating a true fresh checkout) and re-running all three deploy targets' build commands from scratch before pushing the fix — `apps/sdk-docs` and `packages/media-ui-react` were unaffected (TypeDoc reads TS source directly via `tsconfig.json` path mapping, and Storybook stories import relative source files, so neither needs a pre-built cross-package `dist`). All three projects then deployed successfully — see README's Deployed URLs.
- **2026-08-10 — Added a real file download to the Lightbox's Download button (superseding the previous decision that telemetry-only was sufficient).** Once a real Pexels API key was in place and the app was tested end-to-end, it was clear a "Download" button that only fires a tracking event with no visible effect reads as broken, not scoped-down. Verified first that Pexels' CDN sends `access-control-allow-origin: *` on both `images.pexels.com` and `videos.pexels.com` (checked via `curl -I`), so `apps/web/src/download-media.ts` fetches the file as a blob and triggers a save via a `blob:` URL — this forces a real download regardless of the CDN's own `Content-Disposition` header, which a plain cross-origin `<a href download>` can't reliably do. `LightboxOverlay` calls this and only fires the `download` telemetry event (`onDownload`/`useTrackMediaEvent`) after a successful download, with a loading/disabled state and an inline error message if the fetch fails.
